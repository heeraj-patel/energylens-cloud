# Cloud operations

Use current private role configuration and verify commands against the Cloud launcher before changing a service.

For a local API or worker run through `../energylens-dev-bash-scripts/run-energylens-cloud.sh`, copy `.env-example` to `.env-local`, fill the required settings, and run `chmod 600 .env-local`. The launcher selects this file by default when present; pass an explicit private env path to override it. Check with `./run-energylens-cloud.sh api --check` or `worker --check` from the scripts checkout. For concurrent API and worker processes, use a separate worker env with a distinct bind port. Keep migration credentials in a separate `cloud-migrate.env` and pass that file to the `migrate` role.

One Go binary serves path-routed API modules on a single TLS listener. `GET /v1/energy/rates` remains public. With Postgres and OIDC configured, the API serves authenticated account and home routes. Hub enrollment and owner claim routes use their existing proof and ownership checks; Hub-only ownership, sync, telemetry, attachment, runtime, catalog and usage-fact routes additionally require a verified client certificate. `GET /healthz` and `GET /readyz` are probes.

## Datawiz JSON request and fact operations

Apply migrations through 0082 with the dedicated Cloud migration role before enabling this flow. Set `ENERGYLENS_CLOUD_DATAWIZ_REQUESTS_DIR` to an absolute, private directory on a `worker` role (or development `all`) with `ENERGYLENS_CLOUD_DATABASE_URL`. A pass runs at startup and every five seconds. It writes fresh UUID-named JSON files atomically under `resolve/`, `device/`, `zip/`, `savings/`, and `efficiency/`. `resolve/` includes active real appliances, including category-only identities, and named appliances in imported demo snapshots. A new appliance version, attachment revision, usage answer, or administrator queue action writes a fresh resolve request. The marker table prevents repeated files for unchanged saved records; the resolve queue preserves explicit re-requests.

For a one-pass export without starting a server or worker, set `ENERGYLENS_CLOUD_DATABASE_URL` and run `energylens-cloud export-datawiz-requests -output /private/path/requests`. The command uses the same producer and prints `requests_written`; a repeated pass with unchanged saved records prints zero. To request one existing real or simulated appliance again, run `energylens-cloud queue-datawiz-resolve -appliance <uuid> [-output /private/path/requests]`. Without `-output`, the worker writes the file on its next pass. With `-output`, the command writes only that appliance's queued resolve file immediately and reports `requests_written: 1`.

The Cloud worker only creates request files. Process them with the separate Datawiz CLI in realtime mode using its configured Cloud database, for example `python -m energylens_datawiz process-directory --input-dir /private/path/requests --mode realtime`; processed files move to the sibling `requests-done/` tree. For an immediate single-appliance result, run Datawiz `resolve-appliance --appliance-id <uuid> --requests-dir /private/path/requests`. Check `GET /v1/homes/{home}/appliances/{appliance}/energy-resolution` as the owner or `GET /v1/hubs/{hub}/energy-resolutions/{appliance}` with the Hub certificate; 404 means no resolution has been published for the appliance's current version. After an appliance edit, process its new resolve request before expecting an energy value. A real metering attachment always takes precedence over a fallback estimate. To inspect published approved observations, run `energylens-cloud read-datawiz-current -route device -subject 'device:<manufacturer-key>:<model-key>'` with the Cloud database URL configured. Keep request files and database credentials private.

Export the category registry for Datawiz or an offline Hub with `ENERGYLENS_CLOUD_DATABASE_URL=... energylens-cloud export-energy-categories > /private/path/energy-categories.json`. The owner `GET /v1/energy-categories` returns grouped picker labels; the mTLS Hub `GET /v1/hubs/{hub}/energy-categories` returns the full export. Both use a version ETag and accept `If-None-Match`. Appliance saves register unknown category keys in the shared database. If a category is absent in a consumer, export again and check the category API ETag before rerunning its sync or resolve wave.

## Roles and listeners

`go run ./cmd/energylens-cloud --role=api` serves API routes. `--role=worker` serves probes and can run the opt-in metered rollup job. `--role=all` combines them for development. The default role is `all`, or `ENERGYLENS_CLOUD_ROLE` when set. Production refuses `all`. `ENERGYLENS_CLOUD_ENV` is `dev` by default; set `staging` or `production` explicitly in deployment.

The Cloud listener binds to `ENERGYLENS_CLOUD_BIND` (default `127.0.0.1:18091`) and serves owner and Hub routes on the same TLS listener. It requires `ENERGYLENS_CLOUD_TLS_CERT`, `ENERGYLENS_CLOUD_TLS_KEY`, and `ENERGYLENS_CLOUD_HUB_CLIENT_CA`; TLS requests a client certificate and verifies it when supplied. Hub-only handlers also require a verified certificate and retain their durable revocation and ownership-epoch checks. Owner routes require OIDC bearer authentication (or the explicitly enabled local auth verifier). The listener strips client-supplied identity headers. `ENERGYLENS_CLOUD_HUB_BIND` is obsolete and causes startup validation to fail; do not configure a second Cloud listener.

API and worker roles open one shared Postgres pool when `ENERGYLENS_CLOUD_DATABASE_URL` is set. Staging and production require the database URL and certificate-verified TLS (`sslmode=verify-full` with a trusted CA). Startup checks the database and the existing `energy_rate_cache` migration; `/readyz` checks database reachability. Development without a database keeps the existing in-memory rate cache. Set `EIA_API_KEY` for live EIA lookup. The dated July 2026 Texas published average remains the fallback for the phase-1 pilot; it is not a household tariff.

`ENERGYLENS_CLOUD_METERED_ROLLUP_ENABLED=true` explicitly enables bounded hourly/daily recomputation and guarded retention on the `worker` role (or development `all`) with a database. It is false by default. A pass starts immediately and repeats every minute, with a 30-second deadline and bounded batch/bucket/purge counts. Validate migration 0031 and the rollup/retention behavior against the deployment database before enabling it; no live deployment has done so yet.

OIDC account routes require `ENERGYLENS_CLOUD_OIDC_ISSUER`, `ENERGYLENS_CLOUD_OIDC_AUDIENCE`, and `ENERGYLENS_CLOUD_OIDC_JWKS_URL` together. Production API startup requires OIDC or explicitly enabled EnergyLens local authentication; staging and production OIDC settings require HTTPS issuer and JWKS URLs. OIDC tokens must carry a valid RS256 signature, issuer, audience, expiry, and subject. Accounts are keyed by `(issuer, subject)`; verified email is mutable profile data. There is no authentication bypass. Home mutations require a UUID `Idempotency-Key`; PATCH also requires a strong numeric version `If-Match` ETag.

Owner API deployments also require `ENERGYLENS_CLOUD_METERED_EXPORT_CURSOR_KEY_FILE` for metered-export pagination. Generate a dedicated key file with at least 32 cryptographically random bytes (for example, `umask 077; head -c 32 /dev/urandom > /secure/path/metered-export-cursor.key`), mount the same persistent file on every API replica, and keep it across restarts. The file must be private (`0600` or stricter) and cannot share a path with the hub or local-auth signing key. Startup fails if an owner API route is enabled without a valid key. For rotation, set the new active file and `ENERGYLENS_CLOUD_METERED_EXPORT_PREVIOUS_CURSOR_KEY_FILE` to the old file on every replica; remove the previous file setting once old cursors no longer need to work. Unsigned cursors issued before this change are rejected, so clients must restart pagination.

## Migrations

Run `ENERGYLENS_CLOUD_MIGRATION_DATABASE_URL=... energylens-cloud migrate` with a separate DDL-capable migration role before starting API or worker processes. The binary embeds migrations through 0082; 0075 creates the category registry, 0076 stores Datawiz energy resolutions, 0077 allows edited catalog links, 0078 creates the durable resolve queue, 0079 records the nearby Hub device an appliance was added from, 0080 widens re-resolution reasons and adds refresh attempts and the Datawiz source state, 0081 adds the air purifier category, and 0082 lets Datawiz write catalog and fact tables. It serializes migration runs, records SQL checksums in `energylens_schema_migrations`, and rejects changed files. It never runs DDL during serving. A preexisting database without a ledger is safely baselined by reapplying the idempotent 0016/0017 migrations and recording them.

`go test ./...` covers rate behavior, OIDC and account routes, role policy, same-listener TLS access, header stripping, signed annual and usage-fact import lifecycles, active owner/Hub usage-fact reads, catalog response generation and digests, and migration file IDs. PostgreSQL integration tests use `ENERGYLENS_CLOUD_TEST_DATABASE_URL` where configured and otherwise skip; set it to run database-backed migration, import, and API tests. No production deployment or production RDS validation is documented here.

First-party auth remains disabled by default. The [local auth foundation](internal/account/LOCAL_AUTH_FOUNDATION.md) documents the file-backed key gate, a database-free `energylens-cloud check-local-auth-keys` operator check, and the signing key rotation sequence. The check validates proposed material; it does not enable routes or change a deployment.

For persistent local username accounts, use the [local Cloud templates and launcher guide](../energylens-dev-bash-scripts/README.md) with `RUNTIME_ENV=local`. Prepare a persistent private PostgreSQL database, a dedicated application role, a separate DDL migration role, and a separate disposable test database. Configure an HTTPS certificate trusted by the intended client, Hub client CA, persistent Ed25519 signing files, distinct local audience, registration/login rate keys, and metered-export cursor key. Keep these files and the PostgreSQL data volume across restarts and back them up together; startup does not generate or replace keys. The local worker requires its database settings without API signing, OIDC, or mail settings.

Run `./run-energylens-cloud.sh migrate --check`, `api --check`, and `worker --check` from the scripts checkout with the corresponding private role env files. The API check validates the key snapshot offline through `check-local-auth-keys`; none of these checks connects to the database or starts a listener. Once the migration check accepts a local/private PostgreSQL endpoint, run the existing `migrate` command with the DDL role, then start API and worker separately. A configuration check failure requires correcting the private env file or persistent key material before retrying. Never use the application credential for migrations or a production database for local tests.

To switch an existing verified development account to a local username, first make a restorable database backup and preserve the current API, worker, and launch settings. Keep the app and migration PostgreSQL roles distinct. When moving an existing database to those roles, change ownership and grants only for objects in that Cloud database; do not run cluster-wide `REASSIGN OWNED` for a shared administrator role. Configure `~/.config/energylens/cloud-migrate.env` with `RUNTIME_ENV=local`, `ENERGYLENS_CLOUD_ENV=dev`, and the migration role URL. Run `./run-energylens-cloud.sh migrate --check` followed by `./run-energylens-cloud.sh migrate` to apply migration 0073. Then use the migration role to run `energylens-cloud adopt-dev-account-username --user-id <existing-user-uuid> --username <approved-name> --password-stdin`, supplying the existing password on standard input. The command keeps the account and its homes, and accepts an identical repeat. It requires the account's verified development identity and refuses a conflicting credential.

Start the API and worker with their separate private env files. Verify the HTTPS certificate against the local CA and the current client origin, then check `/readyz` and `/v1/auth/config`. Log in at `/v1/auth/local/login` with `username` and `password`; confirm `/v1/me` and `/v1/homes` identify the existing account and home. Check that refresh rotates the refresh token and that logout revokes the access session. If startup fails, restore the prior launch settings and binary from the saved copies; restore the database backup only when reverting the database migration or account adoption. A changed LAN address needs a certificate SAN and mobile origin/pin update before client acceptance.

Local username login permits 15 attempts per account in a one-hour bucket and 20 attempts per source in a separate one-hour bucket. Successful and failed attempts both count. An exceeded bucket returns the same HTTP `401 invalid_credential` as a wrong password. Wait until the bucket's `window_start` is more than one hour old before retrying, or, for the approved `dev` local account during pilot testing, use the separate migration role with `RUNTIME_ENV=local` and the API's existing `ENERGYLENS_CLOUD_LOCAL_AUTH_LOGIN_RATE_KEY_FILE` to run `energylens-cloud unlock-dev-username-login --user-id a225d5f0-22b7-4080-b5d6-e69ce7741b4c --username dev`. The command requires an exhausted bucket, the verified development identity, and the active local username credential. It clears only that account bucket; source limits, password, and sessions remain in effect. Reserve login attempts for the owner and current simulator/phone acceptance after an unlock.

For the shared A9 API service, deploy a tested binary built for `linux/amd64` from the currently deployed source revision with the intended patch. Copy the current `/home/nikesh/energylens-pilot/bin/energylens-cloud-api` to a unique timestamped backup, replace only that binary, and restart only `systemctl --user energylens-cloud-api.service`. Check `/readyz` and `/v1/auth/config` through the configured private CA. If the new API fails, copy the backup over the active binary and restart the same user service; leave the Hub service and its files untouched.

## Hub device trust and ownership

Hub keys are registered only through an operator action using the dedicated migration/provisioning PostgreSQL role. There is no HTTP key-registration endpoint. After applying migrations, run:

```sh
ENERGYLENS_CLOUD_MIGRATION_DATABASE_URL='postgres://...' energylens-cloud provision-hub \
  --local-hub-id elhub_example --public-key '<unpadded-base64url-Ed25519-key>' --approved-by '<administrator-id>'
```

The command returns the cloud hub UUID and a one-use enrollment nonce. Deliver both to the hub operator over an approved provisioning channel. The nonce expires after 15 minutes; `issue-hub-enroll-nonce --hub-id <uuid>` issues another for an already registered, nonrevoked hub. Production provisioning uses certificate-verified PostgreSQL TLS. Configure distinct migration/provisioning and API database roles; the command refuses the API role when both DSNs are configured. Keep stdout with the nonce out of routine logs.

The Cloud listener accepts signed enrollment requests only for registered keys and issued nonces. It signs a 24-hour client certificate using `ENERGYLENS_CLOUD_HUB_SIGN_CERT` and `ENERGYLENS_CLOUD_HUB_SIGN_KEY`; the signing CA must chain to `ENERGYLENS_CLOUD_HUB_CLIENT_CA`. The same listener accepts certificate renewal and `GET /v1/hubs/{hub}/ownership`, with verified-client-certificate middleware on Hub-only handlers. The renewal route checks the stored serial, revocation, expiry, hub identity SAN and ownership epoch, then revokes the prior certificate when issuing the new one. The ownership route returns the claimed home only to a certificate at the current epoch; an old certificate may renew once but cannot read the new home binding. After a verified hub peer is identified, a revoked or stale certificate yields `403 ownership_revoked`, while an unbound or tombstoned home/account yields `404 ownership_unbound`. The hub uses only these explicit codes to purge old-owner staging. A TLS rejection has no HTTP body, so the hub retains its bounded local lease until expiry.

After applying migration 0074, a claimed Hub can publish its current RFC1918 IPv4 LAN HTTPS origin and leaf certificate SHA-256 through `PUT /v1/hubs/{hub}/connection` on the same mTLS listener. The body contains only `https_origin` and `certificate_sha256`; the server derives the home and epoch from the current registered Hub certificate. Publish at startup, after certificate renewal, and at least once per minute. The owner-scoped `GET /v1/homes/{home}/hubs` includes a `connection` hint for at most ten minutes, bounded by the publishing certificate expiry. If the hint is missing, verify the Hub's current certificate, claim epoch, LAN certificate pin, and publish result before retrying. A connection hint helps Mobile locate the Hub; the Hub still checks the owner's current Cloud session for customer requests.

An authenticated account owner begins a claim for one of their homes. The hub's authenticated local pairing channel issues a random possession proof and signs the challenge with its registered Ed25519 key. Cloud verifies the signature, proof hash, owner and expiry before atomically consuming the challenge and assigning the hub. The first claim advances epoch 1 to 2; unclaim advances the epoch again and revokes certificates. A newly claimed hub can use its still valid preclaim certificate once to renew at the new epoch. Claim, finish and unclaim mutations require UUID `Idempotency-Key` headers, and unclaim requires the current strong version `If-Match` value.

Claimed-Hub customer access also uses `POST /v1/hubs/{hub}/owner-authorizations`:
the Hub presents its current mTLS certificate and forwards the owner's bearer
session with `{home_id}`. This exchange currently requires a live local username
session family; unsupported session profiles are denied. The response is
`no-store` and validates the account, home, Hub, certificate and ownership epoch
on each check. If access fails after a claim, verify certificate renewal and
ownership sync, then explicitly re-pair Mobile at the current epoch. A pairing
token alone cannot authorize a claimed home's customer routes.
